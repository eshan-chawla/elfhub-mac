## Overview

macOS desktop companion app — **desktop-first and bring-your-own-key**. Shows a chat-first main window on launch (every saved chat in the sidebar; the three model layers, modes and everything else under Settings) plus a menu bar status item whose floating panel hosts the compact `CompanionPanelView` for quick access. Uses push-to-talk (ctrl+option by default, configurable) to capture voice, transcribes it with the user's chosen speech-to-text layer, and sends the transcript + a screenshot of the display the mouse cursor is on (when the model can see images) to the user's chosen language model. Replies stream as text and are spoken sentence by sentence with the chosen voice. A click-through overlay shows a pointer directly at UI elements the model references, draws annotations (boxes, circles, arrows, underlines, notes) in the Elf's pen — Annotation Orange, the only orange in the app —, and shows a top-center status pill — on any connected monitor. There is no mouse-following cursor.

There is no elfhub server, account or analytics. The only network requests the app makes are API calls to the services the user configures (or to model servers on their own Mac), plus OpenAI's sign-in (`auth.openai.com`) when the user chooses "Continue with ChatGPT" to use their ChatGPT plan, and — for Elfs with the web switched on — the web search the user picked in Settings › Tools & capabilities (DuckDuckGo's plain results page by default; Firecrawl, Brave, Tavily, Exa, their own SearXNG or Firecrawl server; or the model's own search inside the model call) and the web pages Elfs open (only pages they were led to; never the user's own network). The published app also checks GitHub Releases for a newer version once a day (Sparkle; off switch in Settings › General), and on-device speech and voice models are downloaded from Hugging Face when the user presses Download, or moves on from onboarding's voice step with "Download a natural voice" ticked (anonymously). Keys and the ChatGPT sign-in live in the Keychain; chats are saved only on the Mac. When an unexpected error happens, elfhub may offer an error report (below), which only opens GitHub's new-issue page in the user's browser when they choose to; nothing is sent by the app. Token counts and estimated costs of model requests (Settings › General › Usage and cost) are kept only on this Mac.

- **ChatGPT plan ("Continue with ChatGPT")**: OpenAI's Sign in with ChatGPT for open-source local apps lets requests use the user's ChatGPT plan instead of a key. `ChatGPTPlanAccount.shared` signs in through the system browser (OIDC discovery, PKCE, dynamic client registration — `client_id=dynamic_agent_client` the first time, then the issued `oaiapp_…` id — a stable `urn:uuid:` host id, a one-shot `LoopbackOAuthCallbackListener` on `127.0.0.1:<port>/auth/callback`), verifies the ID token (RS256 against the JWKS, issuer, audience, expiry, nonce — `ChatGPTPlanIDTokenValidator`), keeps `ChatGPTPlanCredentials` and the `ChatGPTPlanRegistration` as JSON in the Keychain, renews the hourly access token ≤5 min before expiry through one shared in-flight task (refresh tokens rotate), clears tokens only on terminal refresh errors, and revokes the session on sign-out (keeping the registration). One account; "Use a different ChatGPT account" signs in as a new registration and replaces the saved one only once that succeeds (revoking the old session). The listener only accepts a callback carrying the sign-in's `state`; a renewal that finishes after sign-out revokes the token it got. Plan use needs the granted `chatgpt.tokens.use.direct` scope; allowing it after a decline re-runs OAuth with `prompt=consent` (`startSignIn(requestingPlanConsent:)`). Token failures during a turn count as plan errors (terminal refresh → `credentialRejected`, temporary → `usageTemporarilyUnavailable`), so they reach the fallback too. `OpenAIResponsesLanguageModelProvider` (`LanguageModelProviderKind.chatGPTPlan`) calls `POST /v1/responses` under the plan's preview rules: `store:false`, `stream:true`, the system prompt as `instructions`, no `max_output_tokens`/`temperature`, tools in one `elfhub_screen` namespace, `include: reasoning.encrypted_content`; output items are kept verbatim (`.openAIResponsesRawItem`, ids stripped except reasoning) for the tool follow-up; a reply counts only on `response.completed`; plan errors (`ChatGPTPlanUsageError`: usage limit, unavailable, not eligible, unsupported capability, …) come from HTTP bodies or `response.failed`, and the usage limit is never retried. Fallback: the user picks a fallback model on the card; `ProviderConfigurationStore.configurationForNextTurn()` (`LanguageModelTurnRouting`) answers with it while the plan can't be used and for an hour after the plan hit its usage limit or proved ineligible (`ChatGPTPlanUnavailableReason`, recorded only when a switch happens; other plan errors move just that turn), then tries the plan again; a new sign-in ends the pause; the active model never changes. When the plan fails mid-turn, `CompanionTurnPipeline.runTurn` reruns the model part on the fallback (same screenshot if it fits the fallback's `ModelVisionProfile`, else a new one), `CompanionManager` stops the spoken reply, `TextChatViewModel.restartExchangeAfterLanguageModelSwitch` keeps any partial reply as interrupted, and a `LanguageModelSwitchNotice` shows as a pill hint (not repeated over running actions) and a dismissible notice in the chat whose turn switched (`LanguageModelSwitchChatNotice`; after the usage limit it has a Manage usage button); the fallback's answer goes into that same chat. UI: `ChatGPTPlanCard` at the top of the language-model layer (onboarding and Settings › Models: Continue with ChatGPT, model picker from `/v1/models`, "Using ChatGPT plan" + Manage usage, fallback picker; the ChatGPT model is created and made active only right after a sign-in, via `consumeNewlyCompletedSignIn()`) and the one-time `ChatGPTPlanWelcomeSheet`. Speech-to-text and voice are not covered by the plan. The button shows the ChatGPT logo when an approved `ChatGPTLogo` asset is added to `Assets.xcassets`.
- **On-device models**: `OnDeviceModelAssistant` talks only to Ollama on localhost (`/api/version`, `/api/tags`, `/api/pull` NDJSON progress via `OllamaPullProgressAccumulator`, `/api/show` capabilities, `/api/delete`) to download recommended models (`OnDeviceModelCatalog`) and make one active; also pre-downloads Apple's SpeechTranscriber model (`AppleOnDeviceSpeechModelInstaller`, macOS 26+).
- **Guidance Encoding**: models with tool calling get `point_at` / `annotate` / `perform_screen_action` function tools (`GuidanceToolDefinitions`, `ToolCallGuidanceDecoder`); others use text tags (`TagGuidanceDecoder`). Models with tool calling also get the elf's own tools (`ElfFileTools`); `ElfAgentLoop` runs them and feeds results back over up to three rounds; guidance calls are answered "shown" and a tools-only reply is asked once more, replaying the assistant turn verbatim (Claude thinking blocks preserved via `anthropicRawBlock`). Each round's held-back speech is flushed (`StreamingReplyPresenter.markEndOfModelRound`); history stays one exchange per turn with a footnote of the files changed.
- **Turn Pipeline**: `CompanionTurnPipeline` runs capture → model → decode → normalize → consent → placement → history for both voice and chat; `CompanionPromptBuilder` builds the prompt per coordinate convention and guidance encoding. Screenshots are prefetched at push-to-talk key-down and retaken if the cursor moved to another display before the turn is sent (`shouldReusePrefetchedScreenCaptures`). Reopening a saved chat replaces the pipeline history with that chat's recent exchanges (`replaceConversationHistory`).
- **Speech-to-Text**: runtime-switchable `TranscriptionProviderChoice` — on-device Apple (`SpeechAnalyzerTranscriptionProvider` on macOS 26+, `AppleSpeechTranscriptionProvider` before; the default), AssemblyAI with your key, or any OpenAI-compatible `/audio/transcriptions` endpoint (`WhisperTranscriptionEndpointPreset`: OpenAI, Groq, local faster-whisper).
- **Text-to-Speech**: streaming and sentence-by-sentence — `StreamingReplyPresenter` feeds `SpokenSentenceSegmenter` (strips guidance tags, holds back half-written ones) into `StreamingSpeechPlayer`, which prepares the next sentence while the current one plays and falls back to the on-device voice on failure. Voices: Apple on-device (`AVSpeechSynthesizer`, voice picked in the `SystemVoiceChooserSheet` and stored in `SystemVoiceSettings`; the default — with no voice picked it speaks with the most natural installed voice for the user's language, `SystemVoiceCatalog.mostNaturalVoice`: Premium before Enhanced, their region first, never novelty, else the system default; shown as "Automatic (name)"), ElevenLabs with your key (voices chosen from `ElevenLabsVoicePicker`, never a bare ID field: Automatic, the Recommended presets from `elfhub/ElevenLabsVoicePresets.json` — ElevenLabs' permanent replacements for its Default voices, which stop working on 31 December 2026 and exist only on accounts made before March 2026; edit the file to change `mainElfVoice`, the `sideElfVoices` rotation or the list —, the voices on the user's account listed with their key when a picker appears (`ElevenLabsVoiceDirectory`, `GET /v1/voices`, never in the background or the test host), or a pasted voice ID; a retiring Default voice that's chosen shows a Switch to its replacement; the main Elf's voice is automatic until picked — `CompanionManager.chosenElevenLabsVoiceIdentifier`, 0.0.1's saved Rachel counts as automatic —; each side Elf on ElevenLabs without a voice of its own gets one no other side Elf has, kept in its `ElfLocalSettings.automaticElevenLabsVoiceIdentifier` (`ElevenLabsVoiceAssignment`, `automaticElevenLabsVoiceIdentifier(for:)`), and its settings say which; samples with `previewElevenLabsVoice`), any OpenAI-compatible `/audio/speech` endpoint (`SpeechSynthesisEndpointPreset`: OpenAI, local Kokoro), or off. Network voices play through `NetworkAudioSpeechSynthesisProvider`. Earcons (`CompanionEarcon`) mark accepted / needs-confirmation / failed. **Live captions** (off by default, Settings › Controls "Show live captions"): captions follow the voice, not the model stream — `SpeechSynthesisProvider.playPreparedSpeech(_:onPlaybackProgress:)` reports progress (Apple's voice through `willSpeakRangeOfSpeechString`, audio voices by polling `AVAudioPlayer` about 20 times a second), `StreamingSpeechPlayer.onSentenceSpeechProgress` turns it into word-aligned counts, and `CompanionManager` sends `.spokenCaptionAdvanced` only while the setting is on; a reply that isn't spoken (voice off, or an Elf's own voice off) is always shown as `.unspokenCaptionAvailable` as it streams. `ScreenGuidanceOverlayModel.liveCaptionTranscript` feeds `LiveCaptionPanel`; the pill shows only listening / thinking / acting / hints and hides once speech starts; captions clear on a new turn, Esc or acting, 4 s after speech ends, or after a reading time for unspoken text.
- **On-device speech models (MLX)**: downloadable speech-to-text and voice models from Hugging Face, run with mlx-audio-swift. `OnDeviceComputeProfile` (chip + memory → `ComputeTier`), `OnDeviceVoiceModelCatalog` (recommended picks per tier with license/credit, pasted-repo parsing, voices from a model's `voices/` folder or the catalog, the clearest ones first — `featuredVoiceIdentifiersByModelIdentifier`, Kokoro's six, also onboarding's list), `OnDeviceVoiceModelStore` (downloads with progress into `~/Library/Application Support/elfhub/VoiceModels` in the engine's `mlx-audio/<owner>_<name>` layout, delete, active model and voice per layer), `OnDeviceVoiceModelRuntime` (actor: one job at a time — loads, unloads and inference take turns, so a preload and a recording never load a model twice or share the GPU; loads each layer's model once with `TTS.loadModel` / `STT.loadModel`, sentence → WAV, push-to-talk PCM → text). Wired in as "On-device model" in both layers (`TranscriptionProviderChoice.onDeviceModel`, `SpeechOutputMode.onDeviceModel`, and an elf's own voice `ElfSpeechChoice.onDeviceModel`) through `OnDeviceVoiceModelLayers` (one shared store and engine; preloads the chosen models at launch and when chosen; a voice that isn't ready falls back to Apple's on-device voice) and `OnDeviceVoiceModelSection` (Settings › Models and onboarding: this Mac's chip and memory, recommended models with the best fit first, download / cancel / use / delete, voice picker, any other Hugging Face model by name).

Each elf has a home folder, `~/Library/Application Support/elfhub/Elfs/<id>/` (the unit-test host's `CompanionManager` gets a throwaway one, `elfsDirectoryForThisProcess`, so test runs never create, move or change the real Elfs — and the chat store and action log default to throwaway folders there too, `CompanionManager.isRunningUnitTests`, since a throwaway roster would otherwise turn every real side-Elf chat into a main chat; Paths are checked with `resolvedURLInsideHome` (no `..`, absolute paths or symlinks out; it returns the resolved path, so a link swapped in after the check can't redirect a write); text is size-capped. `ElfManager` (owned by `CompanionManager`) builds `ElfPromptContext` from disk every turn, off the main actor — name, soul, the user's settings for it, profile, a skills index (capped at `skillsIndexCharacterBudget`) plus skill bodies within a budget — which opens the system prompt (`CompanionPromptBuilder.systemPrompt(…, elfPromptContext:)`); the screen-text safety rule and all mechanics (coordinates, tools, notepad) stay app-owned so editing the soul can't remove them. `ElfExporter` writes a `.elf` (format 2, `ElfPackage`): always the config, soul.md, skills/ and files/; user.md unless switched off; chats with that elf only when switched on; never keys, access.json, `.elfhub/` or links. `ElfImporter` previews and installs one after `ElfImportValidator` has checked it. - **The main Elf's memory** (`MainElfMemory.swift`): every Elf's notes about the user live in `user.md` (0.0.1's `profile.md`, renamed once per Elf by `ElfHome.createIfNeeded`; old `.elf` files' `profile.md` imports as `user.md`; 12,000 characters). ### Key Architecture Decisions

**Desktop-first, no server**: Every request goes from the app straight to the user's chosen API (with their key from the Keychain, or their ChatGPT sign-in: `auth.openai.com` for sign-in, renewal, signing keys and sign-out, `api.openai.com` for models and replies) or to a server on their Mac. The ChatGPT sign-in's loopback listener binds only to `127.0.0.1` and runs only during a sign-in. Elfs with the web on (side Elfs by default, main only if switched on) also send their search words to the web search picked in Settings › Tools & capabilities (`WebSearchSettings`: DuckDuckGo with no key by default, Firecrawl, Brave, Tavily, Exa, the user's SearXNG or Firecrawl server, or off) — or, when the user picked "the model's own search" and the elf runs on Claude with the user's key, search inside the model call with Claude's web search tool (`web_search_20260209`, run by Anthropic, `ElfAgentLoop.providerWebSearch`; Elfs on other models use DuckDuckGo; the ChatGPT plan's and Gemini's own search aren't wired yet) — and fetch the pages they were led to (`FetchPageURLPolicy`; hosts resolved and checked so nothing on the user's network is reached). The main Elf's memory and chat titles send chat text to that same chosen model in the background (both switchable in Settings › Privacy & permissions). Nothing else is contacted — no account or analytics — except the update check below, and Hugging Face when the user presses Download on an on-device speech or voice model (anonymously: `OnDeviceVoiceModelStore` never sends a Hugging Face token). "Get a key" / "Get Ollama" links open in the user's browser; the app never fetches them.

**Updates (Sparkle)**: only the published app (`com.elfhub.os`, `AppUpdatePolicy.isSelfUpdatingBuild`) runs the updater; Xcode and contributor builds never update (a release would replace them with a different app). `Info.plist` sets `SUFeedURL` (`https://github.com/eshan-chawla/elfhub-mac/releases/latest/download/appcast.xml` — the newest release's asset), `SUPublicEDKey`, daily checks on without asking (`SUEnableAutomaticChecks`), automatic installs off (`SUAutomaticallyUpdate`; Sparkle's window shows the notes with Install / Remind me later / Skip) and `SUVerifyUpdateBeforeExtraction`. Every update must match the EdDSA key and the same Developer ID. `AppUpdateController` (owned by `CompanionManager`) wraps `SPUStandardUpdaterController` for the app menu's "Check for Updates…" and the Updates card in Settings › General; the defaults key `ElfhubUpdateFeedURL` points it at a local test feed. `scripts/release.sh` signs the stapled DMG with `sign_update` (private key in the maintainer's login Keychain; it stops if that key doesn't match `SUPublicEDKey`), writes `appcast.xml` with `scripts/sparkle/make-appcast.swift` (one item, markdown notes from `ELFHUB_RELEASE_NOTES_FILE`) and uploads both; build numbers come from the previous appcast so they only go up. The app is Apple-silicon only, so each appcast item carries `sparkle:hardwareRequirements arm64` and an Intel Mac is never offered it. "Get a key" / "Get Ollama" links open in the user's browser; the app never fetches them.

**Menu Bar Panel Pattern**: The companion panel uses `NSStatusItem` for the menu bar icon (the igloo glyph, `MenuBarIcon` in the asset catalog — a vector SVG template image built by `scripts/icon/make-menu-bar-icon.swift`, matching the app icon) and a custom borderless `NSPanel` for the floating control panel. This gives full control over appearance (dark, rounded corners, custom shadow) and avoids the standard macOS menu/popover chrome. The panel is non-activating so it doesn't steal focus. A global event monitor auto-dismisses it on outside clicks. Until setup is complete it only offers "Finish setup", which opens the main window (`MainWindowPresenter`, which creates the window again if needed).

**Guidance Overlay**: One full-screen, transparent, click-through `OverlayWindow` per screen hosts `ScreenGuidanceOverlayView` (pointer at target, annotations, status pill). It's non-activating, joins all Spaces, is hidden from Accessibility, never steals focus, and is mounted whenever the app is ready (onboarded + required permissions) so pointing works from voice and text chat alike. It draws nothing when there is no guidance. Windows rebuild on display changes.

**Global Push-To-Talk Shortcut**: Background push-to-talk uses a listen-only `CGEvent` tap instead of an AppKit global monitor so modifier-based shortcuts like `ctrl + option` are detected more reliably while the app is running in the background. The chosen shortcut is cached in memory (`BuddyPushToTalkShortcut.currentShortcutOption`) because the tap reads it on every key event.

**Shared URLSession for AssemblyAI**: A single long-lived `URLSession` is shared across all AssemblyAI streaming sessions (owned by the provider, not the session). Creating and invalidating a URLSession per session corrupts the OS connection pool and causes "Socket is not connected" errors after a few rapid reconnections.

**Guidance Lifetime**: `ScreenGuidanceOverlayModel` keeps the pointer up ≥3 s and until speech ends + 1 s; annotations linger 8 s after speech; everything clears on the next turn or Esc. Esc stops everything, not just marks (`CompanionManager.stopEverythingOnEscape`): a push-to-talk recording is dropped unsent, a voice or typed reply that is thinking or streaming is cancelled (saved as interrupted: the text that streamed stays in its bubble, the screen steps already taken stay listed under it — `StoredChatMessage.screenSteps`, reported live through `runTurn(onScreenStepPerformed:)` / `ComputerUseSession.onStepPerformed` — and "You stopped it here, after N steps on screen" marks the point, `wasStoppedByUser`, `ReplyScreenStepsAndStopView`; a request stopped mid-stream throws URLSession's "cancelled", so `ReplyStopDetection` treats any error from a cancelled turn as a stop, never an error bubble, spoken error or error report), speech stops and the pill clears; the listen-only Esc tap runs only while something can be stopped (`shouldListenForEscape`: guidance visible, voice state not idle, or a typed reply streaming) (`UserInterruptionMonitor`, listen-only while only marks are visible).

**Action Safety**: Actions are resolved against the real UI before firing (Accessibility title/role, password fields, default buttons, the web page host inside browsers; keystrokes are judged by the focused element), judged by pure `ConsentPolicy` (scoped to the user's words — negated ("don't send it") and noun ("draft a reply") uses don't authorize; a typed newline counts as Return; the model's label can only add caution; secrets, Secure Event Input and privacy-blocked apps are always the user's step), previewed with the pointer for ~350 ms, and stoppable instantly: while acting, `UserInterruptionMonitor` runs an active tap that consumes Esc and treats any untagged physical input as the user taking over. Approval is bound to what was shown: every action is re-resolved right before it fires; if the first target is no longer the approved element nothing fires, and if a later action became riskier (`ConsentPolicy.requiresFreshApproval`) the chain pauses and re-arms the card. Only the newest turn may act (`ScreenActionCoordinator.beginTurn` token, called by `CompanionTurnPipeline.runTurn`; a new chain waits for a stopped one to unwind). A spoken answer to a card goes through `SpokenConfirmationParser` (any "no" wins; a consequential action needs its verb said back, "yes, send it"). Most precise channel first: native buttons are pressed with `AXPress` and long plain text is inserted with Accessibility (`AccessibilityElementActions`, never in web content), else tagged synthetic events; key combos are strict (unknown keys refused), follow the current keyboard layout (`UCKeyTranslate`) and press real modifier keys; the pointer returns where the user left it if they didn't move it. Every decision and outcome goes to the local action log (`ComputerUseAuditLog`, `ActionLog.jsonl`, never typed text; Settings › Privacy & permissions). Typing clears modifier flags and yields between characters.

**Dual-Hosted UI, Shared Components**: The main window hosts `MainAppView` (chat first: the sidebar is the chat list, with a Tutorial row while it runs, and the detail pane the active chat; a banner in the chat links to Settings › Models while no model is ready; Support and Settings buttons at the bottom of the sidebar, Settings last; Settings — also ⌘, — swaps the sidebar to `SettingsCategory` pages with a "Back to …" row (and Esc / ⌘[) to the chat, Elf page or tutorial via `MainAppNavigation`; every page except the chat uses `MainAppPage`, one fixed reading column centered in the pane, so content never shifts; onboarding takes over the detail pane until setup completes), while the menu bar panel hosts compact `CompanionPanelView` via `NSHostingView`. Both share row-level components from `CompanionPanelComponents.swift`; the model-layer UI (`ModelLayerCard`, `SpeechToTextLayerSection`, `LanguageModelLayerSection`, `TextToSpeechLayerSection`, `OnDeviceLanguageModelAssistantView`, `PushToTalkShortcutPicker`) lives in `ModelLayerComponents.swift` and is shared by onboarding and the Models section. Other surfaces deep-link into the main window via `CompanionManager.showMainWindow(section:)`.

**Provider Configuration**: `LanguageModelProvider` protocol decouples `CompanionManager` from any specific LLM. `ProviderConfiguration` models a user-editable endpoint (optionally tagged with its catalog `presetIdentifier`); secrets live in the Keychain (`KeychainSecretStore`) keyed by config id — never in UserDefaults or the bundle. The ChatGPT plan configuration has no key: its provider asks `ChatGPTPlanAccount` for a fresh token per request, and its readiness is the sign-in (`ProviderConfigurationStore` re-publishes the account's changes). Saved choices from earlier builds keep loading (legacy raw values / ignored hosted fields).

**Screen Action Consent**: CLICK/KEY actions parsed from replies only execute through `ScreenActionCoordinator`'s per-turn consent gate — context alone is never consent; the user's own words must ask elfhub to *do* something. Parsing lives in pure, unit-testable `ScreenActionParsing`; how much consent each action needs is decided only by `ConsentPolicy` from the real target.

### Interaction Modes

`CompanionManager.InteractionInputMode` — Voice / Text / Both (persisted, defaults to Both). Text-only removes the push-to-talk event tap entirely (`updatePushToTalkMonitorActivation`) and cancels in-flight dictation; `hasPermissionsRequiredForActiveModes` drops the mic requirement in text-only so readiness doesn't falsely block. **Do NOT run `xcodebuild` from the terminal** — it invalidates TCC (Transparency, Consent, and Control) permissions and the app will need to re-request screen recording, accessibility, etc.

**Bundle ids and releases**: the published app is `com.elfhub.os` (final — never change it; `Config/Shared.xcconfig`, and `scripts/release.sh` passes it on the command line). Xcode builds on the maintainer's Mac use `com.elfhub.os.dev` from the gitignored `Config/Local.xcconfig`, so the installed release and the dev build keep separate permissions. Releases are Developer ID signed, notarized DMGs on GitHub Releases with a Sparkle `appcast.xml` beside them, made by the maintainer with `scripts/release.sh` — see `scripts/README.md` (the maintainer's full walkthrough lives in the gitignored `private-notes/session_docs/build-sign-notarize-release.md`, present only on their Mac).

**Evaluations**: `evals/` (outside the app target) holds the computer-use evaluation kit — 17 OSWorld-shaped tasks in `evals/tasks/*.json` (multi-step, consent, injection, takeover, privacy; each with input mode, risk tier, expected confirmations and what must not happen), test fixtures in `evals/fixtures/`, a results template, and `evals/summarize.py` (pass@1, pass^3, steps, time, confirmation precision/recall, injection success). Run on a clean macOS VM snapshot per try, as `evals/README.md` describes.

**Private notes**: research (`learnings/`), session docs and plans live in the gitignored `private-notes/` folder and are never published. Put new private docs there; planning tools that write to `docs/superpowers/` are gitignored too, so move anything worth keeping into `private-notes/`.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
- AppKit `NSPanel`/`NSWindow` bridged into SwiftUI via `NSHostingView`
- All buttons must show a pointer cursor on hover
- For any interactive element, explicitly think through its hover behavior (cursor, visual feedback, and whether hover should communicate clickability)

### Do NOT

- Do not add features, refactor code, or make "improvements" beyond what was asked
- Do not add docstrings, comments, or type annotations to code you did not change
- Do not try to fix the known non-blocking warnings (Swift 6 concurrency, deprecated onChange)
- The project is named `elfhub` everywhere (directory, scheme, targets, module). `PRODUCT_NAME` stays `elfhub` — that's the user-facing app brand, not the internal project name.
- Do not run `xcodebuild` from the terminal — it invalidates TCC permissions

## Git Workflow

- Branch naming: `feature/description` or `fix/description`
- Commit messages: imperative mood, concise, explain the "why" not the "what"
- Never attribute work to Claude or any AI: no `Co-Authored-By` trailers, no "Generated with Claude Code", no "added by / committed by / written by Claude" (or any assistant). This applies to commit messages, PR titles and descriptions, code comments, docs and release notes.
