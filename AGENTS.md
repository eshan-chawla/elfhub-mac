## Overview

macOS desktop companion app — **desktop-first and bring-your-own-key**. Shows a chat-first main window on launch (every saved chat in the sidebar; the three model layers, modes and everything else under Settings) plus a menu bar status item whose floating panel hosts the compact `CompanionPanelView` for quick access. Uses push-to-talk (ctrl+option by default, configurable) to capture voice, transcribes it with the user's chosen speech-to-text layer, and sends the transcript + a screenshot of the display the mouse cursor is on (when the model can see images) to the user's chosen language model. Replies stream as text and are spoken sentence by sentence with the chosen voice. A click-through overlay shows a pointer directly at UI elements the model references, draws annotations (boxes, circles, arrows, underlines, handwritten notes), and shows a top-center status pill — on any connected monitor. There is no mouse-following cursor.

There is no elfhub server, account, analytics or update feed. The only network requests the app makes are API calls to the services the user configures (or to model servers on their own Mac), plus OpenAI's sign-in (`auth.openai.com`) when the user chooses "Continue with ChatGPT" to use their ChatGPT plan. Keys and the ChatGPT sign-in live in the Keychain; chats are saved only on the Mac.

## Architecture

- **App Type**: Full macOS app with a native main window (`MainAppView` — chat first: the sidebar lists every elf (the Elves hub, `ElvesSidebarSection`: main first, a "+" menu for a new elf or the Researcher / Writer starters, each elf's page is `MainAppSection.elf(id)`) and then every chat (`ChatConversationSidebarList`, plus a Tutorial row while it runs) with a bottom hover menu for Settings and Quit; no home page; Settings swaps the sidebar to its categories (Models, Modes, Shortcuts, Permissions, Privacy, General) with Back; an AppKit `NSWindow` owned by `MainWindowPresenter` in `elfhubApp.swift` — not a SwiftUI `WindowGroup`, because SwiftUI only recreates a closed `WindowGroup` window when no window is visible and the overlay always is; it opens at launch, on a Dock click (`applicationShouldHandleReopen`) and from every deep link, closing only hides it, and its hosting view uses `sizingOptions = [.minSize]` so pages never resize the window) AND a menu bar status item whose floating panel hosts the compact `CompanionPanelView`. The main window is the management surface (and where onboarding happens); the menu bar panel is the quick-access surface. Both share row-level components from `CompanionPanelComponents.swift` and `ModelLayerComponents.swift`.
- **Framework**: SwiftUI (macOS native) with AppKit bridging for panels, overlay, and secondary windows
- **Pattern**: MVVM with `@StateObject` / `@Published` state management
- **Three Model Layers** (each configured independently in Settings › Models, and in onboarding step 2): speech-to-text (`TranscriptionProviderChoice`), language model (`ProviderConfigurationStore`), text-to-speech (`SpeechOutputMode`). Multimodal is optional — a text-only model still talks and chats; `ProviderConfiguration.supportsVision` decides whether screenshots are sent.
- **Onboarding**: step 1 Your elf (name the main elf, optional emoji and description, optional Researcher / Writer starter elves added at Finish) → step 2 Models (the three layers) → step 3 Shortcuts & permissions (input mode, push-to-talk shortcut, Esc info, permissions, "Your data on this Mac" — `OnboardingDataOnThisMacCard`: save chats (on), save screenshots (off), action log (on), the same settings as Settings › Privacy — and a "Start tutorial" checkbox checked by default) → `CompanionManager.completeOnboarding(startTutorial:)`. People who finished onboarding before step 1 existed and still have an elf called "elf" get a one-time `NameYourElfCard` above the chat (`ElfNamingPrompt`). The main elf's name is used wherever elfhub speaks as itself (prompt, voice preview `ElfVoicePreview`, the action consent card). The optional `GuidedTutorialController` walkthrough (talk → point → Esc → chat → actions) advances itself from `CompanionEvent`s and voice/chat signals; every step is skippable; while it runs it has a Tutorial row in the sidebar; replay from Settings › General.
- **AI Chat**: Provider-agnostic `LanguageModelProvider` (capabilities: vision, tool calling, `ModelVisionProfile`; content-block messages; delta-only streaming; structured tool calls). Claude with your key (direct `/v1/messages`, `fallbacks: "default"` for refusals; on anthropic.com also prompt-cache breakpoints after tools + system and after the earlier conversation, and `output_config.effort` per turn — low for spoken questions, medium when acting — via `CompanionTurnPipeline.reasoningEffort`), any OpenAI-compatible endpoint, or Gemini. Every provider retries 408/409/429/5xx/529 and dropped connections only before anything has streamed (`LanguageModelRetryPolicy`, `LanguageModelHTTPStreaming.openStream`, which a provider can tell not to retry an error that waiting won't fix), reports a normalized `LanguageModelStopReason` (output-limit cut-offs are logged, mid-stream Claude `error` events throw `streamFailed`), and sends each image's label (screen + coordinate space) next to the image; requests default to 8192 output tokens so thinking never truncates a reply. `LanguageModelProviderCatalog` presets (Anthropic, OpenAI, Gemini, OpenRouter, Mistral, xAI, Groq, DeepSeek, Together, Ollama, LM Studio, llama.cpp, custom) fill in base URL / format / defaults; "Detect models" lists models per kind (`LocalModelServerDiscovery`).
- **ChatGPT plan ("Continue with ChatGPT")**: OpenAI's Sign in with ChatGPT for open-source local apps lets requests use the user's ChatGPT plan instead of a key. `ChatGPTPlanAccount.shared` signs in through the system browser (OIDC discovery, PKCE, dynamic client registration — `client_id=dynamic_agent_client` the first time, then the issued `oaiapp_…` id — a stable `urn:uuid:` host id, a one-shot `LoopbackOAuthCallbackListener` on `127.0.0.1:<port>/auth/callback`), verifies the ID token (RS256 against the JWKS, issuer, audience, expiry, nonce — `ChatGPTPlanIDTokenValidator`), keeps `ChatGPTPlanCredentials` and the `ChatGPTPlanRegistration` as JSON in the Keychain, renews the hourly access token ≤5 min before expiry through one shared in-flight task (refresh tokens rotate), clears tokens only on terminal refresh errors, and revokes the session on sign-out (keeping the registration). One account; "Use a different ChatGPT account" signs in as a new registration and replaces the saved one only once that succeeds (revoking the old session). The listener only accepts a callback carrying the sign-in's `state`; a renewal that finishes after sign-out revokes the token it got. Plan use needs the granted `chatgpt.tokens.use.direct` scope; allowing it after a decline re-runs OAuth with `prompt=consent` (`startSignIn(requestingPlanConsent:)`). Token failures during a turn count as plan errors (terminal refresh → `credentialRejected`, temporary → `usageTemporarilyUnavailable`), so they reach the fallback too. `OpenAIResponsesLanguageModelProvider` (`LanguageModelProviderKind.chatGPTPlan`) calls `POST /v1/responses` under the plan's preview rules: `store:false`, `stream:true`, the system prompt as `instructions`, no `max_output_tokens`/`temperature`, tools in one `elfhub_screen` namespace, `include: reasoning.encrypted_content`; output items are kept verbatim (`.openAIResponsesRawItem`, ids stripped except reasoning) for the tool follow-up; a reply counts only on `response.completed`; plan errors (`ChatGPTPlanUsageError`: usage limit, unavailable, not eligible, unsupported capability, …) come from HTTP bodies or `response.failed`, and the usage limit is never retried. Fallback: the user picks a fallback model on the card; `ProviderConfigurationStore.configurationForNextTurn()` (`LanguageModelTurnRouting`) answers with it while the plan can't be used and for an hour after the plan hit its usage limit or proved ineligible (`ChatGPTPlanUnavailableReason`, recorded only when a switch happens; other plan errors move just that turn), then tries the plan again; a new sign-in ends the pause; the active model never changes. When the plan fails mid-turn, `CompanionTurnPipeline.runTurn` reruns the model part on the fallback (same screenshot if it fits the fallback's `ModelVisionProfile`, else a new one), `CompanionManager` stops the spoken reply, `TextChatViewModel.restartExchangeAfterLanguageModelSwitch` keeps any partial reply as interrupted, and a `LanguageModelSwitchNotice` shows as a pill hint (not repeated over running actions) and a dismissible notice in the chat whose turn switched (`LanguageModelSwitchChatNotice`; after the usage limit it has a Manage usage button); the fallback's answer goes into that same chat. UI: `ChatGPTPlanCard` at the top of the language-model layer (onboarding and Settings › Models: Continue with ChatGPT, model picker from `/v1/models`, "Using ChatGPT plan" + Manage usage, fallback picker; the ChatGPT model is created and made active only right after a sign-in, via `consumeNewlyCompletedSignIn()`) and the one-time `ChatGPTPlanWelcomeSheet`. Speech-to-text and voice are not covered by the plan. The button shows the ChatGPT logo when an approved `ChatGPTLogo` asset is added to `Assets.xcassets`.
- **On-device models**: `OnDeviceModelAssistant` talks only to Ollama on localhost (`/api/version`, `/api/tags`, `/api/pull` NDJSON progress via `OllamaPullProgressAccumulator`, `/api/show` capabilities, `/api/delete`) to download recommended models (`OnDeviceModelCatalog`) and make one active; also pre-downloads Apple's SpeechTranscriber model (`AppleOnDeviceSpeechModelInstaller`, macOS 26+).
- **Guidance Encoding**: models with tool calling get `point_at` / `annotate` / `perform_screen_action` function tools (`GuidanceToolDefinitions`, `ToolCallGuidanceDecoder`); others use text tags (`TagGuidanceDecoder`). Models with tool calling also get the elf's own tools (`ElfFileTools`); `ElfAgentLoop` runs them and feeds results back over up to three rounds; guidance calls are answered "shown" and a tools-only reply is asked once more, replaying the assistant turn verbatim (Claude thinking blocks preserved via `anthropicRawBlock`). Each round's held-back speech is flushed (`StreamingReplyPresenter.markEndOfModelRound`); history stays one exchange per turn with a footnote of the files changed.
- **Turn Pipeline**: `CompanionTurnPipeline` runs capture → model → decode → normalize → consent → placement → history for both voice and chat; `CompanionPromptBuilder` builds the prompt per coordinate convention and guidance encoding. Screenshots are prefetched at push-to-talk key-down and retaken if the cursor moved to another display before the turn is sent (`shouldReusePrefetchedScreenCaptures`). Reopening a saved chat replaces the pipeline history with that chat's recent exchanges (`replaceConversationHistory`).
- **Speech-to-Text**: runtime-switchable `TranscriptionProviderChoice` — on-device Apple (`SpeechAnalyzerTranscriptionProvider` on macOS 26+, `AppleSpeechTranscriptionProvider` before; the default), AssemblyAI with your key, or any OpenAI-compatible `/audio/transcriptions` endpoint (`WhisperTranscriptionEndpointPreset`: OpenAI, Groq, local faster-whisper).
- **Text-to-Speech**: streaming and sentence-by-sentence — `StreamingReplyPresenter` feeds `SpokenSentenceSegmenter` (strips guidance tags, holds back half-written ones) into `StreamingSpeechPlayer`, which prepares the next sentence while the current one plays and falls back to the on-device voice on failure. Voices: Apple on-device (`AVSpeechSynthesizer`, voice picked in the `SystemVoiceChooserSheet` and stored in `SystemVoiceSettings`; the default), ElevenLabs with your key, any OpenAI-compatible `/audio/speech` endpoint (`SpeechSynthesisEndpointPreset`: OpenAI, local Kokoro), or off. Network voices play through `NetworkAudioSpeechSynthesisProvider`. Earcons (`CompanionEarcon`) mark accepted / needs-confirmation / failed.
- **The elf (home folder, soul, profile, skills, config)**: the agent is an *elf* (`Elf…` types). Each elf has a home folder, `~/Library/Application Support/elfhub/Elves/<id>/` (the main elf is always `main`, shared by every build like chats are; more elves live side by side, each in its own folder named from its name, `ElfManager` keeps the roster, `ElfEditor` edits one elf), and `ElfHome` is the only code that touches it: `elf.json` (`ElfConfiguration`: identity, behaviour — reply length, tone, language, takes notes, learns skills, file access — and `preferredModels` without keys; every field decodes with a default), `soul.md` (the user's forever instructions; starter = elfhub's original conversation rules; the elf may only suggest changes), `profile.md` (the user's personal preferences, noted by the elf), `skills/<slug>/SKILL.md` (`ElfSkill`, the agentskills.io / Hermes layout: YAML frontmatter `name`, `description`, other keys kept verbatim, then a markdown body — working knowledge; Hermes skill folders can be dropped in; the phase-1 single-file `skills/*.md` are moved into folders once per elf by `migrateLegacySkillFilesIfNeeded`, marked done in `.elfhub/legacy-skills-migrated`), `files/` (its own files), `access.json` (this Mac's folder grants, never exported) and `.elfhub/` (the app's own data about the elf — `local-settings.json` = `ElfLocalSettings`, which of this Mac's models and voices the elf uses; never exported). Elf tools resolve paths with `ElfHome.resolvedURLForElfTool(_:access:)`: `.elfhub/`, `elf.json` and `access.json` are unreachable and `soul.md` is read-only (`ElfHomeError.reservedPath`). Paths are checked with `resolvedURLInsideHome` (no `..`, absolute paths or symlinks out; it returns the resolved path, so a link swapped in after the check can't redirect a write); text is size-capped. `ElfManager` (owned by `CompanionManager`) builds `ElfPromptContext` from disk every turn, off the main actor — name, soul, the user's settings for it, profile, a skills index (capped at `skillsIndexCharacterBudget`) plus skill bodies within a budget — which opens the system prompt (`CompanionPromptBuilder.systemPrompt(…, elfPromptContext:)`); the screen-text safety rule and all mechanics (coordinates, tools, notepad) stay app-owned so editing the soul can't remove them. `ElfExporter` writes a `.elf` zip: always elf.json (with the current setup in `preferredModels`), soul.md and skills/; profile.md and files/ only when switched on; never access.json or symlinks. Each elf's page in the Elves hub (`ElfHubPage`) edits all of it — identity with other names (aliases), how it answers, soul, profile, skills, home folder, export — and deletes side elves (to the Trash). The main elf has tools on its own folder (`ElfFileTools`, run by `ElfAgentLoop`; tags for models without tool calling, `ElfToolTags`): it writes profile.md and files/ freely, saves a skill only when the user asks, and every change goes through `ElfChangeLog` — shown under the reply in chat (`SavedElfFileChange`, Undo) and in the elf's Changes card. Side elves answer when called by name (`ElfAddressRouter` in `CompanionManager.addressedElf`): `CompanionTurnPipeline.runTurn(…, speakingElf:)` uses that elf's folder, prompt (`.sideElfForeground`), tools, four model rounds, its own model (`configurationForNextTurn(preferredConfigurationIdentifier:)`, with a new screenshot when the key-down one is too big for it) and voice (`CompanionManager.speechProvider(for:)`), and the last six exchanges with other elves' replies marked "[Name]" (`historyTurns(forSpeakingElfName:…)`). Chat shows who answered (`StoredChatMessage.speakingElfIdentifier`, emoji + name above the reply), the composer's elf picker (`ChatComposerElfSelection`) overrides the name and resets after sending, and the speech recognizer listens for every elf's names (`ElfAddressRouter.dictationKeyterms`). Next phases: background tasks, the web and the user's folders, `.elf` v2.
- **Chat history**: `ChatConversationStore` saves each conversation as JSON in `~/Library/Application Support/elfhub/Conversations` — typed messages and push-to-talk turns alike (`StoredChatMessage.inputSource`); a voice turn after 30 quiet minutes starts a new conversation. Typed and spoken turns are recorded through the same `TextChatViewModel` exchange API (`beginExchange` → `showStreamingReply` → `completeExchange` / `failExchange` / `saveInterruptedExchange`). Optional, off by default: "Save screenshots with chats" keeps the screenshot each turn sent to the model (`TurnResult.originalScreenshotJPEGData`, before the user's ink) under `Conversations/Screenshots/<conversation id>/<message id>.jpg`. Only one image is stored per question: the pointer and marks a reply drew are saved as vector data on the reply (`SavedScreenGuidance`, display-local AppKit points from `TurnResult.shownScreenGuidance`) and redrawn over that image with the overlay's own views in static mode (`animatesAppearance: false`). The user's own drawing is stored the same way (`SavedUserInk` on the question). In chat, the question gets a collapsed "Screenshot" row (after = the user's drawing) and a reply with marks a collapsed "Screenshot with marks" row (after = drawing + elfhub's marks); both have a Before / After switch (`BeforeAfterPicker`), and clicking opens `ScreenshotViewerSheet` over the chat with the same switch. Saving, screenshots and deletion are in Settings › Privacy. One `TextChatViewModel` (owned by `CompanionManager`) backs both the main window's Chat section (with a conversation list) and the compact chat window.
- **Screen Capture**: ScreenCaptureKit (macOS 14.2+). Only the display under the mouse cursor is captured (`indexOfScreenFrame(containingCursorLocation:in:)` — edges and gaps fall to the nearest screen), so the model sees one image and is never asked for a screen number; the overlay still works on every monitor
- **Drawing while talking**: while push-to-talk is held, `UserScreenInkRecorder` installs an active mouse tap (only between key-down and key-up) that swallows press/drag/up and records `UserInkStroke`s; the overlay draws them live as a solid orange trailing line (`UserInkStrokesView`, `.userInkChanged` / `.userInkFinished` events). On send, `CompanionTurnPipeline` burns the strokes into the screenshot the model receives (`UserInkScreenshotRenderer`); chat history saves the original image plus the strokes as data (`SavedUserInk` on the question, `TurnResult.originalScreenshotJPEGData` / `shownUserInk`) and appends a note to the user's message from `UserInkDescriber` (circled area / line / clicked spot, in the model's coordinate convention). Safety net: a mouse event without the shortcut's modifiers (`BuddyPushToTalkShortcut.areShortcutModifiersHeld`) ends drawing and passes through.
- **Notepad**: the model can write an explanation (steps, commands, code) into a floating window with silent text tags — `[NOTEPAD:title]` then `[NOTEPAD_LINE:markdown]`, strictly alternating with speech (text, line, text, line; each line appears when the sentence before it ends). Every model uses tags for this, even tool-calling ones, because tool calls only arrive after the stream and lines must appear while elfhub talks. `SpokenSentenceSegmenter` attaches each notepad item to the sentence after it (`SpokenSentenceSegment.notepadItemsToShowFirst`) and never joins short sentences across a notepad line; `StreamingSpeechPlayer.enqueue(sentence:onSentenceStarted:)` runs it as that sentence starts (empty sentences only run the action; stopping runs the pending ones so written lines never go missing); with the voice off `StreamingReplyPresenter` shows lines as they arrive. `NotepadItemRevealer` emits `.notepadOpened` / `.notepadLineWritten`, applying the same rules as `NotepadTagParser.notepad(fromResponseText:)` (title only before the first line, at most 40 lines). `NotepadPanelManager` shows a non-activating, key-able `NSPanel` at the top right of the cursor's screen that stays until its X is clicked (turns, Esc and overlay timers don't touch it; a new notepad replaces it), with selectable text and a copy button (plain text; "Copy as Markdown" in its menu); its header is a drag handle (a SwiftUI `DragGesture` that moves the panel by the mouse's screen location, `NotepadWindowDragStart`; the hosting view accepts the first click, since the panel never activates elfhub), and `NotepadPanelModel` paces lines that arrive together so they still appear one at a time. The pipeline strips notepad tags before guidance decoding, returns `TurnResult.shownNotepad`, and appends the notepad to the model's history (the window is never in screenshots); chat saves it on the reply (`StoredChatMessage.notepad`, also from interrupted replies) and shows it whole as `SavedNotepadCard`.
- **Voice Input**: Push-to-talk via `AVAudioEngine` + pluggable transcription-provider layer. System-wide keyboard shortcut via listen-only CGEvent tap; the shortcut (`BuddyPushToTalkShortcut.ShortcutOption`) is user-selectable and persisted.
- **Point · Annotate · Act**: The model embeds `[POINT:...]`, annotation (`[HIGHLIGHT|CIRCLE|ARROW|UNDERLINE|NOTE:...]`) and, in action mode, action (`[CLICK|DOUBLECLICK|SCROLL|TYPE|KEY:...]`) tags. `TagGuidanceDecoder` turns them into `ScreenGuidanceCommand`s; `ScreenGuidanceCoordinateNormalizer` converts the model's coordinate convention (pixels / 0–999 / 0–1000) to screenshot pixels; `ScreenGuidancePlacement` maps them to screen points and refines them with Accessibility (`AccessibilityElementLocator`). Actions go through `ScreenActionCoordinator` → `ConsentPolicy` → `ScreenActionSynthesizer`.
- **Screenshot Geometry**: `ScreenshotGeometry` sizes every capture to the active model's image limits (`ModelVisionProfile`, derived from `ProviderConfiguration`) — never larger, since oversized images are silently resized by providers and coordinates drift.
- **Event Bus**: `CompanionEventBus` carries turn/speech/guidance/action events from `CompanionManager` and `ScreenActionCoordinator` to `ScreenGuidanceOverlayModel`, which owns all on-screen timing (and to `GuidedTutorialController`, and the notepad events to `NotepadPanelManager`). The overlay never reads `CompanionManager` state directly — a future agent loop can drive it by emitting the same events.
- **Concurrency**: `@MainActor` isolation (default actor isolation is MainActor), async/await throughout
- **Build configuration**: `Config/Shared.xcconfig` (committed) includes optional gitignored `Config/Local.xcconfig` for signing team and bundle id. No third-party Swift packages.

### Key Architecture Decisions

**Desktop-first, no server**: Every request goes from the app straight to the user's chosen API (with their key from the Keychain, or their ChatGPT sign-in: `auth.openai.com` for sign-in, renewal, signing keys and sign-out, `api.openai.com` for models and replies) or to a server on their Mac. The ChatGPT sign-in's loopback listener binds only to `127.0.0.1` and runs only during a sign-in. Nothing else is contacted — no account, analytics, or update checks. "Get a key" / "Get Ollama" links open in the user's browser; the app never fetches them.

**Menu Bar Panel Pattern**: The companion panel uses `NSStatusItem` for the menu bar icon (the igloo glyph, `MenuBarIcon` in the asset catalog — a vector SVG template image built by `scripts/icon/make-menu-bar-icon.swift`, matching the app icon) and a custom borderless `NSPanel` for the floating control panel. This gives full control over appearance (dark, rounded corners, custom shadow) and avoids the standard macOS menu/popover chrome. The panel is non-activating so it doesn't steal focus. A global event monitor auto-dismisses it on outside clicks. Until setup is complete it only offers "Finish setup", which opens the main window (`MainWindowPresenter`, which creates the window again if needed).

**Guidance Overlay**: One full-screen, transparent, click-through `OverlayWindow` per screen hosts `ScreenGuidanceOverlayView` (pointer at target, annotations, status pill). It's non-activating, joins all Spaces, is hidden from Accessibility, never steals focus, and is mounted whenever the app is ready (onboarded + required permissions) so pointing works from voice and text chat alike. It draws nothing when there is no guidance. Windows rebuild on display changes.

**Global Push-To-Talk Shortcut**: Background push-to-talk uses a listen-only `CGEvent` tap instead of an AppKit global monitor so modifier-based shortcuts like `ctrl + option` are detected more reliably while the app is running in the background. The chosen shortcut is cached in memory (`BuddyPushToTalkShortcut.currentShortcutOption`) because the tap reads it on every key event.

**Shared URLSession for AssemblyAI**: A single long-lived `URLSession` is shared across all AssemblyAI streaming sessions (owned by the provider, not the session). Creating and invalidating a URLSession per session corrupts the OS connection pool and causes "Socket is not connected" errors after a few rapid reconnections.

**Guidance Lifetime**: `ScreenGuidanceOverlayModel` keeps the pointer up ≥3 s and until speech ends + 1 s; annotations linger 8 s after speech; everything clears on the next turn or Esc. Esc stops everything, not just marks (`CompanionManager.stopEverythingOnEscape`): a push-to-talk recording is dropped unsent, a voice or typed reply that is thinking or streaming is cancelled (saved as interrupted), speech stops and the pill clears; the listen-only Esc tap runs only while something can be stopped (`shouldListenForEscape`: guidance visible, voice state not idle, or a typed reply streaming) (`UserInterruptionMonitor`, listen-only while only marks are visible).

**Action Safety**: Actions are resolved against the real UI before firing (Accessibility title/role, password fields, default buttons, the web page host inside browsers; keystrokes are judged by the focused element), judged by pure `ConsentPolicy` (scoped to the user's words — negated ("don't send it") and noun ("draft a reply") uses don't authorize; a typed newline counts as Return; the model's label can only add caution; secrets, Secure Event Input and privacy-blocked apps are always the user's step), previewed with the pointer for ~350 ms, and stoppable instantly: while acting, `UserInterruptionMonitor` runs an active tap that consumes Esc and treats any untagged physical input as the user taking over. Approval is bound to what was shown: every action is re-resolved right before it fires; if the first target is no longer the approved element nothing fires, and if a later action became riskier (`ConsentPolicy.requiresFreshApproval`) the chain pauses and re-arms the card. Only the newest turn may act (`ScreenActionCoordinator.beginTurn` token, called by `CompanionTurnPipeline.runTurn`; a new chain waits for a stopped one to unwind). A spoken answer to a card goes through `SpokenConfirmationParser` (any "no" wins; a consequential action needs its verb said back, "yes, send it"). Most precise channel first: native buttons are pressed with `AXPress` and long plain text is inserted with Accessibility (`AccessibilityElementActions`, never in web content), else tagged synthetic events; key combos are strict (unknown keys refused), follow the current keyboard layout (`UCKeyTranslate`) and press real modifier keys; the pointer returns where the user left it if they didn't move it. Every decision and outcome goes to the local action log (`ComputerUseAuditLog`, `ActionLog.jsonl`, never typed text; Settings › Privacy). Typing clears modifier flags and yields between characters.

**Dual-Hosted UI, Shared Components**: The main window hosts `MainAppView` (chat first: the sidebar is the chat list, with a Tutorial row while it runs, and the detail pane the active chat; a banner in the chat links to Settings › Models while no model is ready; `SidebarBottomMenu` opens on hover into Settings and Quit; Settings swaps the sidebar to `SettingsCategory` pages with Back to the chat or tutorial via `MainAppNavigation`; every page except the chat uses `MainAppPage`, one fixed reading column centered in the pane, so content never shifts; onboarding takes over the detail pane until setup completes), while the menu bar panel hosts compact `CompanionPanelView` via `NSHostingView`. Both share row-level components from `CompanionPanelComponents.swift`; the model-layer UI (`ModelLayerCard`, `SpeechToTextLayerSection`, `LanguageModelLayerSection`, `TextToSpeechLayerSection`, `OnDeviceLanguageModelAssistantView`, `PushToTalkShortcutPicker`) lives in `ModelLayerComponents.swift` and is shared by onboarding and the Models section. Other surfaces deep-link into the main window via `CompanionManager.showMainWindow(section:)`.

**Provider Configuration**: `LanguageModelProvider` protocol decouples `CompanionManager` from any specific LLM. `ProviderConfiguration` models a user-editable endpoint (optionally tagged with its catalog `presetIdentifier`); secrets live in the Keychain (`KeychainSecretStore`) keyed by config id — never in UserDefaults or the bundle. The ChatGPT plan configuration has no key: its provider asks `ChatGPTPlanAccount` for a fresh token per request, and its readiness is the sign-in (`ProviderConfigurationStore` re-publishes the account's changes). Saved choices from earlier builds keep loading (legacy raw values / ignored hosted fields).

**Screen Action Consent**: CLICK/KEY actions parsed from replies only execute through `ScreenActionCoordinator`'s per-turn consent gate — context alone is never consent; the user's own words must ask elfhub to *do* something. Parsing lives in pure, unit-testable `ScreenActionParsing`; how much consent each action needs is decided only by `ConsentPolicy` from the real target.

### Interaction Modes

`CompanionManager.InteractionInputMode` — Voice / Text / Both (persisted, defaults to Both). Text-only removes the push-to-talk event tap entirely (`updatePushToTalkMonitorActivation`) and cancels in-flight dictation; `hasPermissionsRequiredForActiveModes` drops the mic requirement in text-only so readiness doesn't falsely block. The pipeline (`respondToChatMessage`) is shared by both inputs.

## Build & Run

```bash
# Open in Xcode
open elfhub.xcodeproj

# One-time: copy Config/Local.xcconfig.example to Config/Local.xcconfig and set
# DEVELOPMENT_TEAM + ELFHUB_BUNDLE_IDENTIFIER (a free Personal Team works).
# Select the elfhub scheme, Cmd+R to build and run

# Known non-blocking warnings: Swift 6 concurrency warnings,
# deprecated onChange warning in TextChatView.swift. Do NOT attempt to fix these.
```

**Do NOT run `xcodebuild` from the terminal** — it invalidates TCC (Transparency, Consent, and Control) permissions and the app will need to re-request screen recording, accessibility, etc.

**Bundle ids and releases**: the published app is `com.elfhub.os` (final — never change it; `Config/Shared.xcconfig`, and `scripts/release.sh` passes it on the command line). Xcode builds on the maintainer's Mac use `com.elfhub.os.dev` from the gitignored `Config/Local.xcconfig`, so the installed release and the dev build keep separate permissions. Releases are Developer ID signed, notarized DMGs on GitHub Releases, made by the maintainer with `scripts/release.sh` — see `scripts/README.md` (the maintainer's full walkthrough lives in the gitignored `private-notes/session_docs/build-sign-notarize-release.md`, present only on their Mac).

**Private notes**: research (`learnings/`), session docs and plans live in the gitignored `private-notes/` folder and are never published. Put new private docs there; planning tools that write to `docs/superpowers/` are gitignored too, so move anything worth keeping into `private-notes/`.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
- AppKit `NSPanel`/`NSWindow` bridged into SwiftUI via `NSHostingView`
- All buttons must show a pointer cursor on hover
- For any interactive element, explicitly think through its hover behavior (cursor, visual feedback, and whether hover should communicate clickability)

### Do NOT

- Do not add features, refactor code, or make "improvements" beyond what was asked
- Do not add docstrings, comments, or type annotations to code you did not change
- Do not try to fix the known non-blocking warnings (Swift 6 concurrency, deprecated onChange)
